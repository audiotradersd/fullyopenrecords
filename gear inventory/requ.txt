TASK: Add Gear Inventory to the Fully Open Records artist dashboard

Build a new "Gear" area within the existing Fully Open Records artist dashboard.

PURPOSE

Gear Inventory gives artists a permanent record of the instruments, equipment, software and other tools they use to create music.

Initially this is an inventory/organisation feature.

In future, individual gear items will be assignable to:
- Tracks
- Track versions
- Recording sessions
- Rehearsals
- Live performances

This future relationship is important.

The data model must therefore treat gear as reusable artist-owned entities rather than simply text fields attached to a track.

For example:

ARTIST
  ↓
GEAR INVENTORY
  ├── Fender Telecaster
  ├── Roland Juno-106
  ├── Shure SM57
  ├── Ableton Live
  └── Boss DS-1

Later:

TRACK
  ↓
VERSION: First Jam
  ↓
GEAR USED
  ├── Fender Telecaster
  └── Boss DS-1

VERSION: Demo
  ↓
GEAR USED
  ├── Fender Telecaster
  ├── Shure SM57
  └── Logic Pro

This will eventually allow Fully Open Records to build a genuine historical record of HOW a piece of music was created.

IMPORTANT

Do not design this feature specifically around rock bands.

"Gear" needs to encompass the equipment used across essentially every type of music creation:

- Rock/pop bands
- Electronic music
- DJs
- Hip-hop
- Classical music
- Orchestral music
- Folk
- Jazz
- Experimental music
- Bedroom producers
- Vocalists
- Recording engineers
- Live performers

-----------------------------------
GEAR SETTINGS
-----------------------------------

This is important for the future Track Version Control integration.

An artist may want to remember not only WHICH piece of equipment they used but HOW it was configured.

However, do not store a single permanent "settings" value against the gear item.

A Marshall amp might be used differently on every recording.

Instead distinguish between:

GEAR
"What is it?"

and later:

GEAR USAGE
"How was it configured for this particular track/version?"

For example:

GEAR

Marshall DSL40

TRACK VERSION

Kodiak — Demo 2

GEAR USAGE

Marshall DSL40

Gain: 7
Bass: 5
Middle: 8
Treble: 4
Presence: 6
Master: 3

Photo:
[photo of amplifier controls]

Notes:
"Recorded with the amp facing into the hallway."

This relationship should be anticipated in the database architecture now even if Gear Usage is implemented later.

-----------------------------------
FUTURE TRACK VERSION INTEGRATION
-----------------------------------

Design the schema so we can later create:

track_version_gear

Suggested relationship:

id
track_version_id
gear_item_id
notes
created_at

And potentially:

track_version_gear_settings

track_version_gear_id
setting_name
setting_value

Plus images specific to that usage/session.

Do NOT build the complete Track Version integration unless it is trivial and already fits the current implementation.

The important requirement in this task is that the Gear architecture does not prevent it later.

-----------------------------------
GEAR HISTORY
-----------------------------------

Do not delete the historical identity of equipment simply because an artist no longer owns it.

This is important.

If an artist records an album using a guitar in 2026 and sells the guitar in 2028, the historical album record should still show that guitar.

Therefore provide statuses such as:

Currently Used
Owned
Previously Owned
Sold
Borrowed
Rented

Archived/sold gear should remain available to historical track/version relationships.

Hard deletion should only be possible where doing so will not destroy historical relationships, or appropriate referential handling should be implemented.

-----------------------------------
UX PRINCIPLE
-----------------------------------

Adding gear must not feel like cataloguing an insurance inventory.

The emphasis is:

"These are the tools you make music with."

The UI should feel visual, creative and personal.

Use photographs prominently.

An artist's Gear page should eventually feel almost like looking around their studio.

-----------------------------------
FUTURE PRODUCT DIRECTION
-----------------------------------

Keep the implementation extensible.

Eventually Fully Open Records should be able to answer questions such as:

"What guitar did I use on this demo?"

"What synth patch did I use on the original version?"

"What microphone did we use for these vocals?"

"What pedals were on the board at this rehearsal?"

"What version of this plugin was used?"

"What equipment appears most frequently across my recordings?"

"Show every track I recorded with this guitar."

"How did the setup change between the demo and final recording?"

The current Gear Inventory is the foundation for this.

-----------------------------------
IMPLEMENTATION
-----------------------------------

Before coding:

1. Inspect the existing Fully Open Records application.
2. Identify the dashboard architecture and routes.
3. Identify authentication/artist ownership patterns.
4. Identify existing database conventions.
5. Identify image/file upload infrastructure.
6. Identify existing cards, modals, forms, buttons and filtering components.
7. Reuse existing design tokens and components wherever practical.

Do not create a parallel design system.

Implement using the project's existing stack and conventions.

Ensure:
- gear belongs securely to the authenticated artist/account
- users cannot access another artist's private gear inventory
- responsive design
- accessible forms
- sensible image optimisation
- validation
- appropriate database indexes
- referential integrity
- no unnecessary dependencies
